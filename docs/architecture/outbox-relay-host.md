# Outbox Relay host

`Pernix.OutboxRelay.Host` is the single deployable of the Outbox Relay. It is an ASP.NET Core host that composes configuration, logging, health, telemetry, the Core library, the outbox store providers and the transports, and ships as container image `outbox-relay`. Code lives in `src/Pernix.OutboxRelay.Host/`, `src/Pernix.OutboxRelay.Core/`, `src/Pernix.OutboxRelay.PostgreSql/` and `src/Pernix.OutboxRelay.Kafka/`. Later specs add transports and providers as new projects registered from `Program.cs`.

## Overview

The host covers startup composition, the configuration chain, the diagnostics listener, the OTel pipeline and the container image. Core binds the outbox configuration model, refuses to start on invalid configuration, outbox tables or destinations, and runs one worker per outbox per replica. The PostgreSQL provider validates outbox tables, holds a session advisory lock per outbox, reads rows per `Ordering.Mode`, deletes delivered ones and writes retry state (`retry_count`, `next_attempt_at`, `last_error`) for failed ones. The Kafka transport validates its destinations and sends records. Every `Ordering.Mode` delivers. A leader runs one `DeliveryTerm` per leadership term: read, send, commit outcomes. What it reads and may send next comes from an `IDeliveryOrdering`: `UnorderedDelivery` for `None` (read due rows, send each) and `ScopedDelivery` for `PerKey` and `Strict` (snapshot-gated cursor reads in `(tx_id, id)` order, at most one unconfirmed send per key or per outbox, failed-rows summary and rewind). A message fault spends a retry or, when retries run out or the fault is permanent, sends a dead letter to the outbox's dead-letter destination, then drops the row (`Continue`) or, on `PerKey` and `Strict` only, blocks it (`Block`, `next_attempt_at = 'infinity'`). A destination fault pauses the outbox and spends nothing. A row whose route the destination does not accept is held: nothing is sent, no retry is spent, and it is checked again after `Retry.MaxDelay`. Startup refuses `Block` with `None`. Off the delivery path, the leader of each outbox also reads outbox stats every 15 s on its own pooled connection (`IValidatedOutboxStore.GetStatsAsync`) and reports five gauges from the cached result.

## Interfaces

- **Configuration chain**, last wins: `appsettings.json` + `appsettings.{Environment}.json` → env vars → command line. Loaded once at startup, no reload.
- **Outbox configuration**: root sections `ConnectionStrings`, `KafkaClusters`, `Destinations[]`, `Outboxes[]`. Settings, defaults and rules in [`configuration.md`](../configuration.md#outbox-configuration).
- **Diagnostics listener**: Kestrel endpoint `Diagnostics`, `http://+:5612` (`KESTREL__ENDPOINTS__DIAGNOSTICS__URL`). No application port.
- **Health**: `GET /livez`, `GET /readyz`. Body is `Healthy` or `Unhealthy` only. 503 when unhealthy. Not traced. `/readyz` is 503 before `ApplicationStarted`, after `ApplicationStopping`, and while any worker's latest connect to its outbox database failed. A lock held by another replica does not affect it. `/livez` is 503 if, while the host is not stopping, any worker loop ended or faulted, or any worker is past its `ProgressDueAt`. The check's description names the outboxes. Database and broker outages and delivery pauses do not affect `/livez`. Gate stalls (long transactions holding the `PerKey`/`Strict` gate) affect neither `/livez` nor `/readyz`. A send to a destination with a `SendBound` (Kafka `None` 30 s) counts toward liveness at its deadline + 10 s. Kafka `PerKey` and `Strict` sends have no bound and are exempt. With no outboxes both outbox checks are healthy.
- **Telemetry**: traces and metrics over OTLP, configured by standard `OTEL_EXPORTER_OTLP_*` env vars. Resource `service.name` = `SERVICE_NAME`, overridable by `OTEL_SERVICE_NAME` / `OTEL_RESOURCE_ATTRIBUTES`. Logs are never exported over OTLP. Gauge `outbox.leader`, unit `{leader}`, attribute `outbox`: `1` while this replica leads, `0` otherwise. Counter `outbox.delivered`, unit `{message}`, attribute `outbox`: `+1` per message the original destination confirmed. Counters `outbox.message_faults`, `outbox.destination_faults`, `outbox.dead_lettered`, unit `{message}`, attributes `outbox` and `destination` (original or dead-letter destination): `+1` per message fault, destination fault and confirmed dead letter. Gauges `outbox.pending` (`{message}`, estimate), `outbox.retrying` (`{message}`), `outbox.blocked` (`1`, rows on `Strict`, keys on `PerKey`, do not sum across modes), `outbox.head_age` (`s`), `outbox.gate_lag` (`s`), attribute `outbox` only: reported by the leader only, from a reading at most 30 s old. A failed, stale or non-leader reading emits nothing. `outbox.gate_lag` also emits nothing when the role lacks `pg_read_all_stats` (`pg_monitor`). Meanings and alert conditions in [`configuration.md`](../configuration.md#metrics).
- **Logs**: single-line JSON on stdout, UTC timestamps. Messages may name setting paths, outbox, destination, connection and cluster names, and the configured table. They never contain connection string values, `Producer` values, secrets, keys, payloads or header values. Leadership events carry the outbox name and a sanitized reason only. Delivery events (110–125) add destination name, row id, retry count and error code text. Failure events: `MessageFaulted` 111, `MessageRetryScheduled` 117, `MessageDeadLettered` 118, `DeadLetterFailed` 119, `MessageDropped` 120, `DeadLetterDeferredByStop` 121, `DeadLetterRetryScheduled` 122, `MessageBlocked` 123 (Warning, once per blocked row), `MessageHeld` 125 (Warning, once per hold). `DeliveryRewound` 124 (Debug) logs one line per applied `PerKey` or `Strict` rewind, with reason `summary`, `failure`, `unpark` or `safety`. It carries the first deferred reason, except after an unpause, which applies any waiting rewind at once and logs `unpark`. Stats events carry the outbox name and a sanitized reason: `StatsUnavailable` 130 (Warning, once per change to failing, including at start), `StatsAvailable` 131 (Information, on recovery), `GateLagUnavailable` 132 (Warning, once per outbox per process). No log line per delivered message above `Debug`. librdkafka log lines go to `ILogger`, with syslog debug mapped to `Debug`. With the default `Information` level, output from a domain-set `debug` property appears only when `Logging:LogLevel:Pernix.OutboxRelay.Kafka` is `Debug`. It is not redacted, so that choice is the domain's.
- **Image env contract**: `SERVICE_NAME=outbox-relay`, `SERVICE_VERSION` and `SERVICE_COMMIT` from build args `BUILD_VERSION` and `BUILD_COMMIT`.

### Producer integration

Producers write outbox rows in their business transaction with plain SQL or through the producer client packages ([ADR 0008](../adr/0008-producer-client-packages.md)). The packages ship as NuGet, the relay only as the image. Code lives in `client/` (`net8.0`, lockstep `VersionPrefix` in `client/PackageVersion.props`):

- `Pernix.OutboxRelay.Client`: no package dependencies. `IOutboxPublisher` (`PublishAsync(DbTransaction, ...)`, `PublishEnlistedAsync(DbConnection, ...)` for an ambient `TransactionScope`, single and batch, no publish without a transaction), `OutboxMessage` (`Route`, `WithRoute(route)`: optional route, format `^[a-z0-9][a-z0-9._-]{0,62}$`, checked against the shared vectors `tests/contract-vectors/routes.json`), `OutboxHeaders` (header rules at least as strict as the relay's `HeadersParser`), `OutboxTable`, `OutboxColumns` (V001 column names, `ProducerWritten`, `All`). Route rules live in `client/src/Shared/RouteRules.cs`, compiled into each package by source link.
- `Pernix.OutboxRelay.Client.PostgreSql`: Npgsql and `Microsoft.Extensions.DependencyInjection.Abstractions` only. `PostgreSqlOutboxPublisher` (raw `NpgsqlCommand`/`NpgsqlBatch`, SQL text built once per publisher, never calls `EnlistTransaction`, names `route` only for a routed message), `AddPostgreSqlOutboxPublisher`, `AddKeyedPostgreSqlOutboxPublisher(key, table)`, route-scoped `AddKeyedPostgreSqlOutboxPublisher(key, table, route)` (stamps its route on route-less messages, passes an equal route, throws `ArgumentException` on a different route before any write), and `PostgreSqlOutboxSchema.Scripts(table, namePrefix)`, which renders the embedded `sql/postgresql/V001__create_outbox.sql` for any table and name prefix. The package runs no DDL.
- `Pernix.OutboxRelay.Client.EntityFrameworkCore`: `Microsoft.EntityFrameworkCore.Relational` only, floor `8.0.10` (`VersionOverride`, not the CPM version). `UseOutbox(publisher)` on `DbContextOptionsBuilder` (one line for `AddDbContext`, `AddDbContextPool`, `AddDbContextFactory`, `AddPooledDbContextFactory`), `EnqueueOutbox(OutboxMessage)` on `DbContext`, `IOutboxQueue<TContext>` DI facade (`AddOutboxQueue<TContext>`, route-scoped keyed `AddKeyedOutboxQueue<TContext>(key, route)` with the same route rule at `Enqueue`), and `PublishAsync(DbContext, ...)` on `IOutboxPublisher` for an immediate write in the current EF transaction. The queue is an EF internal service, one per `DbContext` instance, reset per pooled lease. The stateless `OutboxInterceptor` flushes it at `TransactionCommittingAsync` of an EF transaction begun by the context, as the transaction's last writes, in one batch. With queued messages, `SavingChanges` without an EF transaction (also inside a `TransactionScope`) and sync `Commit` refuse. A transaction from `UseTransaction` refuses the queue. Under a retrying execution strategy, `EnqueueOutbox` without a current EF transaction throws. Rollback, failed publish and dispose without commit clear the queue and log `OutboxMessagesDiscarded` (event 1, Warning). See the [ADR 0008 amendment](../adr/0008-producer-client-packages.md#amendment-2026-11-08-ef-core-add-on-spec-2026-11-08-client-ef).
- Route (client 1.1.0): V001 carries producer-written `route text NULL` with CHECK `<prefix>_route_format`. NULL = no route. The relay reads and requires `route` and holds every row its destination does not accept, see [ADR 0009](../adr/0009-explicit-per-row-routing.md) and [Routing](../delivery.md#routing). See the [ADR 0008 route amendment](../adr/0008-producer-client-packages.md#amendment-2026-11-08-route-column-and-route-scoped-services-spec-2026-11-08-client-route).

Consumer guide: [`docs/client-packages.md`](../client-packages.md), every C# block compile-checked by `client/tests/Pernix.OutboxRelay.Client.Docs.Unit.Tests`.

Client packages declare exactly their listed dependencies at their floors, and none packs a CPM transitive pin as a nuspec dependency (`PackageGraphTests.No_client_package_pins_a_transitive_package`). The EF package sets `CentralPackageTransitivePinningEnabled` `false` for this. Relay tests reference the client to guard drift: `OutboxColumnsDriftTests` (relay `RequiredColumns ⊆ OutboxColumns.All`), the shared header vectors `tests/contract-vectors/headers.json` (client rules never looser than `HeadersParser`) and `ClientContract/` integration tests (client-published rows delivered by the relay).

### Extension points for later specs

- Outbox store providers: implement `IOutboxStoreProvider` and register it as a singleton `IOutboxStoreProvider` (see `AddPostgreSqlOutboxProvider`). It is resolved by `Name` from `Outboxes[].Database.Provider`, case-insensitive. A duplicate `Name` fails startup. `SupportedModes` gates `Ordering.Mode`.
- Transports: a new project implements `IDestinationFactory` and `IDestination` and registers the factory as a singleton `IDestinationFactory` (see `AddKafkaTransport`), composed from `Program.cs`. It is resolved by `Transport` from `Destinations[].Transport`, case-insensitive. A duplicate `Transport` fails startup. `IDestination.SendBound` (null: unbounded, untracked by liveness) tells Core how to bound sends. `IDestination.Routes` (null: one address, accepts only rows without a route. Otherwise a non-empty ordinal set of the routes it maps, fixed for the instance) tells Core which rows it accepts. Core holds every other row. A `Transport` value with no registered factory is refused (`transport '<value>' is not implemented in this build`). `Validate(destination, path, relay)` returns the transport's configuration failures: it binds its own block from `DestinationOptions.Settings` with `RelayOptionsBinder.BindSection<T>` and reports any key it does not own as `unknown setting`. `Create(destination, context)` builds an `IDestination`. `DestinationContext.Probe` (`IsProbe` true) marks the startup probe, which must not send. `IDestination.ValidateAsync` throws `DestinationValidationException` with a sanitized message. `SendAsync` returns a `ValueTask<DeliveryResult>` that Core consumes exactly once, and never throws for delivery failures. Core calls it for a main send only with a row the destination accepts, sent to the address of its `Route`. A dead letter goes to the single address, and `Route` is data only. `DisposeAsync` discards unsent messages. Core has no transport enum or `switch`, so no Core edit is needed.
- Interface members: the blocked form of `Outcome.Fail` (`Outcome.Block`) and `ReadRequest.After` use for `PerKey` and `Strict` are done. `GetStatsAsync` on `IValidatedOutboxStore` is done: a provider answers on its own connection, never an `IOutboxSession`'s, bounds the read with its own deadline, honours `ct` at once, and throws only `OutboxStatsUnavailableException` (sanitized) on failure. It returns `GateLag` null with a reason when the engine hides it. A provider that does not know an `Outcome` subtype throws `ArgumentException`.
- Liveness or readiness checks: `AddCheck<T>(tags: [HealthTags.Live])` or `[HealthTags.Ready]`. No endpoint changes.
- Instruments and spans: use `RelayDiagnostics.Meter` and `RelayDiagnostics.ActivitySource` from Core (`Pernix.OutboxRelay.Core.Diagnostics`). Both are already exported.
- `Pernix.*` packages: `PackageGraphTests` fails on any `Pernix.*` package.

## Data model

The host stores nothing. Outbox tables belong to the domain and follow `sql/postgresql/V001__create_outbox.sql`, with or without `V002__drop_destination_columns.sql`. The relay reads the catalog (`pg_class`, `pg_namespace`, `pg_attribute`, `pg_type`, `pg_constraint`, `pg_locks`) and statistics (`pg_stat_get_live_tuples`, `pg_partition_tree`, `pg_stat_activity`, `pg_prepared_xacts`, `pg_has_role`), deletes delivered, dead-lettered and dropped rows, and writes `retry_count`, `next_attempt_at` (`now() + delay` from the database clock) and `last_error` on failed rows, only where `retry_count` is still the value it read. It runs no DDL. A row with `retry_count` above `Retry.MaxRetryAttempts` and not held (`last_error` not starting `route not mapped: `) is dead-letter pending.

- **`None` read**: due rows (`next_attempt_at <= now()`), `ORDER BY id`, excluding held ids (`id <> ALL(@exclude)`, at most 10 × 1000). `None` has no gate, so a row can commit behind any cursor. The from-head read is an accepted cost.
- **`PerKey` and `Strict` read (gate)**: one statement, `tx_id < pg_snapshot_xmin(pg_current_snapshot())`, `(tx_id, id) > (@after_tx, @after_id)` (dropped at the head), `ORDER BY tx_id, id LIMIT @max`, served by `outbox_tx_id_id_idx`. `Strict` returns rows in any state with `IsDue = (retry_count = 0 OR next_attempt_at <= now())` and `NextAttemptAt` null for `'infinity'`. `PerKey` scans at most `@max` rows from the cursor in an inner `ORDER BY tx_id, id LIMIT @max` and returns every scanned row with `IsDue` = the row is due (`retry_count = 0 OR next_attempt_at <= now()`) and its key has no failed row not yet due (`NOT EXISTS ... OFFSET 0` through `outbox_failed_message_key_idx`, one probe per scanned row). Payload and headers come back only for due rows. NULL keys hold nothing. `'infinity'` never reaches a client `DateTime`.
- **Failed-rows summary**: at most once per `Polling.Interval`, `count(*)`, a checksum `sum(hashint8extended(id, retry_count × 4 + blocked × 2 + due))` over `id`, `retry_count`, the blocked flag (`next_attempt_at = 'infinity'`) and the due flag (`next_attempt_at <= now()`), and the earliest future finite `next_attempt_at` over `retry_count > 0`. A change from the term's baseline rewinds the cursor to the head (on `PerKey` mid-walk, once the walk reaches the gate frontier, or 60 s after the walk's last progress).
- **Blocked rows**: `Outcome.Block` commits `UPDATE ... SET retry_count = @retry_count, next_attempt_at = 'infinity', last_error = @error WHERE id = @id AND retry_count = @read_retry_count`, set-based, in the group transaction. `'infinity'` appears only as a SQL literal. A blocked row has `retry_count >= 1` and is never sent again.
- **Stats statement**: one statement, no parameters, built per mode and `relkind`, one round trip and snapshot on the stats connection. Failed rows (`retry_count > 0`, `outbox_failed_message_key_idx`): `Retrying` = not `'infinity'`, `Blocked` = `0` (`None`), blocked rows (`Strict`) or distinct blocked non-null keys plus blocked NULL-key rows (`PerKey`). `Pending` = `GREATEST(live − failed, 0)`, `live` = `pg_stat_get_live_tuples(table)`, or for a partitioned table the sum over `pg_partition_tree(...) WHERE isleaf` (a parent's own count is always `0`). `HeadAge` = `now() − created_at` of the first row by `ORDER BY id` (`None`) or `ORDER BY tx_id, id` (`PerKey`, `Strict`), `LIMIT 1`, any state, `0` when empty. `GateLag` = oldest `now() − xact_start` over `pg_stat_activity` with `backend_xid` set, excluding its own backend, and `now() − prepared` over `pg_prepared_xacts`, cluster-wide, `0` when none, visible only when `pg_has_role('pg_read_all_stats', 'USAGE')`. `pg_is_in_recovery()` refuses a standby. The failed-row aggregate scans every failed row, so its cost grows linearly with failed rows. Measured on PostgreSQL 17.11: p95 13–50 ms at 100k failed rows and 66–268 ms at 500k. See the bullet "Keep failed rows well below 500k per outbox" in [Operator actions](../delivery.md#operator-actions).

The session executes the read texts above with positional parameters: the `None` read binds `$1` max and `$2` exclude, a `PerKey` or `Strict` head read binds `$1` max, and a `PerKey` or `Strict` cursor read binds `$1` max, `$2` after_tx and `$3` after_id.

No new DDL: V001 indexes serve the gate, cursor, `PerKey` probe, summary and stats statement.

Advisory lock key: `pg_try_advisory_lock(hashtext('outbox-relay'), hashtext(<schema-qualified table>))`. The table name is the one PostgreSQL resolves for the connection's role, so `outbox` and `public.outbox` share a lock. The key does not depend on the outbox `Name`.

## Operational notes

- Kubernetes probes: `GET :5612/livez`, `GET :5612/readyz`. SIGTERM flips readiness to 503. A leader stops reading and drains sends in flight until T0 + 20 s, starts no new dead letters (rows that need one stay untouched, `DeadLetterDeferredByStop`), runs remaining commits and the dispose of both destinations (no flush) concurrently until T0 + 25 s, and closes its session by T0 + 27 s, all measured from the stop signal T0. A session dispose that started without a stop (lock loss, or the close after a worker fault) is re-capped at T0 + 27 s when the stop arrives mid-dispose (`AwaitSessionDisposeAsync`, shared by `LoseAsync` and `CloseAsync`). A hung dispose is then abandoned and logged `LeadershipReleasePending` ("session close abandoned at stop deadline"). A dispose that completes as the stop arrives keeps its own outcome and is never run twice. Workers log `LeadershipReleased` (or `LeadershipReleasePending`, event 107, when an abandoned command still holds the connection, the unlock failed or timed out, the connection was broken, the close failed or hit its deadline, so the lock may stay held until the server ends the backend) and the host stops within `HostOptions:ShutdownTimeout` (default and minimum `00:00:28`, a lower value fails startup). Pod termination grace must be at least 30 s.
- Delivery liveness: every worker stamps `ProgressDueAt` before each await (now + the step's bound + 10 s grace). Bounds: start delay 2 s, session commands 5 s, session dispose 10 s (unlock under the command deadline, then close), lock retry wait up to 5 s, destination dispose on lock loss 5 s, delivery loop wait up to the next 1 s lock check (so `Polling.Interval` and pauses never extend it), and on stop the time left to the phase deadline. Separately, the earliest in-flight send deadline (start + the destination's `SendBound`, main or dead-letter) is due at that deadline + 10 s (`TrackSendDeadline`): Kafka `None` 30 s (`message.timeout.ms`). Kafka `PerKey` and `Strict` sends are exempt (`SendBound` null, `TrackSendDeadline(null)`), because they have no timeout and a restart during a broker outage would only cause duplicates. A worker past its due time fails `/livez`. Gate stalls do not affect `/livez` or `/readyz`.
- Delivery failures: a message fault spends a retry (row updated, due again after backoff) or, when permanent or out of retries, is dead-lettered and deleted, or deleted without a dead letter when `DeadLetter.Destination` is unset (message lost). A failed dead letter leaves the row dead-letter pending. With `Block` (`PerKey`, `Strict`) the row is dead-lettered first when configured, then blocked instead of deleted, and holds its key or outbox until an operator deletes or resets it. A destination fault, including `Local_MsgTimedOut` (Kafka `None` only), leaves the row untouched and pauses the outbox for `min(Retry.InitialDelay × Retry.BackoffMultiplier^(n−1), Retry.MaxDelay)`. On `PerKey` and `Strict` the parked row stays its scope's next send after the pause. A timed-out Kafka `None` send that landed is sent again (duplicate). Operator actions are plain SQL, and on ordered outboxes a delete or reset of a failed row is picked up by the next summary. See [Failure policy](../delivery.md#failure-policy) and [Operator actions](../delivery.md#operator-actions).
- Lock loss during delivery: the term drops its held rows, cursor, summary baseline and uncommitted outcomes and disposes its destination and dead-letter destination without flushing, within 5 s. A commit transaction cut by the loss applies nothing. The next term builds a new producer and, for `PerKey` and `Strict`, reads from the head. Sends of the old term that land late are duplicates and can arrive out of order. First deliveries per scope stay in gate order.
- Startup validation runs in `StartingAsync`, before Kestrel listens and before any worker starts. Stages run in order: configuration, then tables and databases, then destinations, then destination bounds and routes. Invalid configuration, a missing table or column (`route` included), a relay column whose type or nullability differs from V001, a standby, the same table or lock key under two outboxes, an unreachable outbox database, a missing or undescribable topic, a topic describe timeout, an invalid producer configuration, or a destination that declares `SendBound` ≤ 0 for an outbox, an empty `Routes` set or a route key not matching `^[a-z0-9][a-z0-9._-]{0,62}$`, or a dead-letter destination that declares `Routes`, logs one `StartupFailed` line and exits `1`. The line lists every failure of the first failing stage. The generic host also logs its own start-failure entry for the same exception. A bad config source or a port bind failure does the same. Expect `CrashLoopBackOff`.
- Gate stalls: a long or forgotten write transaction, or a prepared transaction, anywhere on the PostgreSQL cluster stops every `PerKey` and `Strict` outbox there. Domains set `idle_in_transaction_session_timeout`.
- `Strict` keeps total order only on a one-partition topic. The relay does not check the partition count.
- PostgreSQL needs a direct connection to a primary. No RDS Proxy, no PgBouncer transaction pooling, because session advisory locks do not survive them ([ADR 0003](../adr/0003-leadership-by-postgresql-session-advisory-lock.md)). A standby is refused. Sessions force `Pooling=false`, `Load Balance Hosts=false`, `Target Session Attributes=read-write` for host lists, 5 s timeouts, and server keepalives (`tcp_keepalives_idle` 5, `tcp_keepalives_interval` 2, `tcp_keepalives_count` 3, `tcp_user_timeout` 11000). The stats connection forces the same settings except pooling (`MaxPoolSize=1` per outbox) and the server keepalive `SET`: it takes `tcp_keepalives_idle`, `tcp_keepalives_interval` and `tcp_keepalives_count` as startup `Options` instead, without `tcp_user_timeout`.
- Leadership: first lock attempt after a random 0–2 s delay. A failed attempt retries after `min(0.5 s + 0.5 s × locks this replica holds, 5 s)`. A leader checks its session every 1 s and never releases its lock except on shutdown or session loss. Outboxes are not rebalanced between running replicas.
- Takeover bounds: graceful shutdown or crash, up to 5 s. Network loss, about 11 s for PostgreSQL to free the lock plus up to 5 s. The old leader stops leading within 6 s, before the lock is freed.
- Alert on `outbox.leader` summed across replicas other than `1` per outbox.
- Stats: one pooled stats connection per led outbox per replica (`application_name` `outbox-relay-stats:<outbox>`), kept open between reads (60 s idle lifetime > 15 s cadence), closed within about 70 s of the replica losing the lock. A failed, hung or slow stats read only makes the five gauges absent (event 130). It never affects the lock, the 1 s check, the session deadline, delivery, `/livez`, `/readyz` or the stop budget. Without `pg_monitor` (or `pg_read_all_stats`) the relay starts, logs 132 and reports no `outbox.gate_lag`.
- An unreachable or unset OTLP collector does not affect startup or health.
- A config change needs a restart.
